# Методика измерения рассинхрона (Фаза 0) — каналы, пределы, цепочка

Источник времени рана: **QPC хоста** (`time.perf_counter_ns`). Wall-clock логируется один раз на сессию; w32tm-синхронизация на время длинных тестов отключается или логируется (NTP-степ посреди дрейф-теста делает данные мусором).

## Цепочка измерений

```
QPC хоста ──> лог flip'ов стенда (i → perf_ns)
                 │  (экран, машиночитаемая полоса Gray-24 + 2 якоря)
                 ▼
        кадры MP4 камеры ──> decode_stand (idx на кадр)
                 │
                 ▼
        PTS контейнера / GPMF (STMP/CORI) / TC-трек
```

Семантика STMP «прибивается» отдельным экспериментом (E3): decoded stand idx ↔ STMP того же кадра на серии клипов; до этого STMP не используется в выводах. Важно: автор gpmf-parser (dnewman) прямо заявил, что STMP «was not intended for post synchronization» (issue #80) → основной путь пост-выравнивания = TC-трек + MP4 stts + per-frame стримы (CORI/SHUT); STMP — вспомогательный, E3 лишь характеризует его пригодность.

## Каналы и их пределы

| Канал | Предел (мс) | В долях кадра @30/60/120/240 fps | Ограничение |
|---|---|---|---|
| Экранный счётчик (этот монитор, 60 Гц*) | 16.7 | 0.50 / 1.0 / 2.0 / 4.0 | квант = refresh; НЕ субкадровый канал |
| Экранный счётчик @240 Гц (если появится) | 4.2 | 0.125 / 0.25 / 0.5 / 1.0 | тот же квант |
| Аудио clap/chirp (48 кГц, AAC) | ~0.1–1 (реалистично) | ≤0.03 / 0.06 / 0.12 / 0.24 | акустика: 2.92 мс/метр; A/V-офсет камеры калибруется физическим клапом (E4) |
| Экранная «вспышка» | ~5–20 | — | LCD scanout 16.7 мс + response 5–15 мс размывают фронт; для T_readout НЕвалидна (red-team #3) |
| LED-строб + полосы rolling shutter (Ф1) | 0.3–0.5 (лит.) | 0.01–0.015 @30fps | требует LED (Arduino), выдержка ≤1/480, HyperSmooth OFF |
| GPMF STMP | 0.001 (номинал) | — | per-payload, семантика до E3 не доказана |
| TC-трек (Labs QR / сток Quik) | ~кадр | 1 | метаданные, не экспозиция |

\* фактический refresh фиксируется стендом в заголовке лога (`display_hz_reported`) и перепроверяется по плотности flip'ов.

## Правила честности

1. **Только относительные величины.** DWM/панель/WASAPI добавляют неизвестные константы; они сокращаются в разностях камера-vs-камера и в джиттере повторов. Абсолютные офсеты не публикуются.
2. **Эталон одновременности** — физическое событие в кадре (клап) или общий LED; никогда не «бип из колонок + вспышка экрана».
3. **HyperSmooth/EIS OFF** на всех измерительных клипах (EIS переставляет строки — ломает полосные измерения и геометрию полосы).
4. fps в анализе — точные рациональные (29.97/59.94...), из ffprobe `r_frame_rate`.
5. Каждая опубликованная цифра — с σ и пределом канала; DONE засчитывает только `tools/verify_phase0.py` (пересчёт из сырых MP4).

## Что каждый эксперимент отдаёт

- **E1 джиттер старта**: распределение (mean/σ/min/max) `t_display(первый кадр) − t_cmd`; канал = счётчик (квант 16.7 мс) → оценка σ честна на уровне «кадр @30fps»; субкадровая точность здесь и не нужна.
- **E2 дрейф**: наклон `camera_PTS vs stand_time` за ≥20 мин → ppm ± CI95; квант канала входит в остатки фита, на наклон почти не влияет (усреднение сотен точек).
- **E3 монитор+STMP**: скорость/направление scanout (съёмка @240fps), связка decoded idx ↔ STMP.
- **E4 аудиоканал**: повторяемость A/V-офсета камеры по 20 клапам одной записи; выход — σ канала, не абсолют.
