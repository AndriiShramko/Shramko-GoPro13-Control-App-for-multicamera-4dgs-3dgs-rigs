# Labs serial-шелл и NCM живут на ОДНОМ интерфейсе (MI_00) — переключение рвёт NCM-драйвер Windows

## Открытие (доказано на живой HERO13, fw H24.01.02.10.70)

`$SHEL=1` (Labs USB command shell) и HTTP-over-USB (NCM) — это **один и тот же USB-интерфейс MI_00**, взаимоисключающие:
- В NCM-режиме MI_00 = «UsbNcm Host Device» (сеть) → HTTP API на 172.2x.y.51:8080.
- После `$SHEL=1!SAVE` + reboot MI_00 = «USB Serial Device (COM5)» → командный шелл 115200 8N1. HTTP при этом НЕДОСТУПЕН.
- `$SHEL=0!SAVE` + reboot возвращает NCM — НО на Windows драйвер повторно НЕ привязывается автоматически (CDC NCM → Error 28, как при первой установке): каждое переключение = ручной re-bind или перевтык USB.

## Что через serial-шелл работает (проверено)

- `oT<YYMMDDHHMMSS.mmm>oTD0oTZ<tz>` — **установка часов с миллисекундами ПО ПРОВОДУ** (это и есть цель «мс-часы по USB без QR»). Эхо команды, часы встают.
- `$p:T` — чтение переменной времени (секунды).
- Латентность serial-команды: mean ~900 мс, σ ~400 мс (n=15) — это ЛАТЕНТНОСТЬ ТРАНСПОРТА (USB-serial round-trip + обработка), НЕ точность установки часов. Для точного момента нужен `!S`/`!<time>S` (старт по значению часов), не «отправить в нужный момент».

## Критические выводы для 100-камерного рига

1. **Нельзя одновременно иметь HTTP-контроль И serial-шелл на одной камере.** Выбор режима — архитектурное решение:
   - HTTP/NCM: удобное управление (запись/скачивание/настройки/статус), но часы только 1 с.
   - Serial-шелл: мс-часы и Command Language по проводу, но нет HTTP (запись — командами `!S`/`!E`, скачивание — вынимать карту или переключать режим).
2. **Переключение режимов ломает NCM-драйвер Windows** → на площадке не переключать в цикле; выбрать режим один раз. Linux (cdc_ncm/cdc_acm из коробки) переключение переносит лучше — ещё довод за Linux-хосты на риге.
3. **Мс-синхру лучше делать МОМЕНТ-QR или GPS**, а не serial-«отправить в нужный момент»: латентность транспорта σ 400 мс убивает попытку «послать oT точно в T». Правильно: часы выставить (QR/serial/GPS, точность самой установки ±1 кадр по докам), а СТАРТ привязать к значению часов через `!<time>S` (Labs исполнит по своему кварцу) — тогда транспортная латентность не важна.

## Практический рецепт (сформируется после E7/Labs-тестов)

Скорее всего: NCM-режим для управления + Precision-Time-QR с монитора для ресинка часов (±1 кадр) + `!<time>S` синхростарт по часам + пост-выравнивание аудио/вспышкой для субкадра. Serial-шелл — для разовой конфигурации/отладки, не для боевого цикла.

## Дополнение 2026-07-13: Labs QR-сканер живёт на превью-конвейере

QR-команды перестают сканироваться, когда превью-конвейер камеры спит (после записи/скачивания/простоя экран-превью гаснет). **Рецепт пробуждения без человека: `GET /gopro/camera/stream/start?port=8554`** — включает конвейер сенсора, сканер снова читает QR с монитора (проверено: !OR исполняется). Это же объясняет старые провалы batch-QR-тестов «камера не сканит без wake».
